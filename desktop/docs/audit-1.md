### E1 Hypothesis Assessment
- **H6 (Hand-built UI per feature):** **Strongly Confirmed.** UI coverage is `24.2%` of the curated Harness contract (`6.7%` across all engine surfaces), far below the 50% threshold. Every view (`SwarmView`, `AutomationsView`, `TelegramView`, `SettingsView`, `PluginsView`) is hand-built against local/mock state instead of schema-driven registry renderers.
- **H1 (Two sources of truth):** **Supported.** Settings (`desktop-settings.json` vs `config.toml`), sessions (`desktop-sessions.json` vs daemon), sidebar/archives, swarm, automations, and telegram all maintain Desktop-only state stores disconnected from the engine.
- **H2 (Lossy protocol):** **Partially Supported / Nuanced.** Between the internal daemon (`99 Request / 103 ServerEvent`) and `rayucode-harness-api` (`52 ApiRequest / 56 ApiEvent`), 47 requests and 47 events are not exposed on the curated API; however, the *much larger* loss is Desktop itself dropping `42 / 56` (`75%`) of the structured `ApiEvent`s that the engine *already* emits (including `model_info`, `permission_mode_changed`, `connection_phase`, `background_progress`, `text_replace`).
- **H4 (Hardcoded UI assumptions):** **Supported.** Desktop hardcodes 10 slash commands, 9 local preference keys, and 10 tool matchers rather than reading a registry.
- **H3, H5, H7, H8:** Not directly tested by E1 (though E1 surfaced `auth-bridge.ts`'s duplicated cloud agent loop for H5 and `text_replace` / `connection_phase` drops relevant to H8).

### What Could Not Be Verified in E1
- Dynamic MCP tools discovered at runtime from external MCP servers (`~/.rayu/mcp.json`) were not enumerated because they depend on user-configured servers.
- Runtime feature-flag gating (`FeatureConfig`) and OS-conditional tools (e.g., `macos_computer_use` on non-macOS) were evaluated statically from source.

### E2 Hypothesis Assessment
- **H4 (Hardcoded UI assumptions):** **Strongly Confirmed.** 357 engine-derived hardcoded literals exist across 15+ production files, directly causing the UI to display values the engine never uses (`claude-opus-5-5`, `Medium`, `kvWarmPct: 94`, `0.08 cr`, `200k`, `"Auto"` effort, `54.2%` analytics).

- **H5 (Duplicated logic):** **Partially Supported.** `desktop/electron/auth-bridge.ts:1085-1460` contains a complete second agentic chat/tool loop talking directly to `/anthropic/v1/messages` with its own 4 local workspace tools (`list_files`, `read_file`, `search_files`, `run_command`), hardcoded `max_tokens: 4096`, `maxRounds = 6`, and 45s watchdog — duplicating Rust engine logic in Electron.
- **H2, H3, H6, H7, H8:** Not primary targets of E2.

### E10 Hypothesis Assessment
- **H1 (Two sources of truth):** **Strongly Confirmed.** Across 9 of 11 tested cells (and 100% of effort cells and active-session model cells), the UI dropdown displays a local value that contradicts the engine's effective value and actual provider request. Even for permission mode, Desktop never reconciles against `ApiEvent::PermissionModeChanged` or per-session server state.
- **H4 (Hardcoded UI assumptions):** **Strongly Confirmed.** UI exposes settings/defaults (`claude-opus-5-5`, `Medium`, `Auto`, `default`) disconnected from engine capabilities, and silently hides engine errors (`main.ts:294,307`, `daemon-client.ts:977,994`).
- **H5 (Duplicated logic):** **Supported.** Electron's `streamCloudChat` fallback completely bypasses both effort and permission mode policy.
- **H8 (Lack of guaranteed terminal/status visibility):** **Partially Supported.** Mid-turn `set_model`/`set_reasoning_effort` deferrals in Rust have no "pending until next turn" status event in `ApiEvent` (unlike `ServiceTierChanged { pending }` in internal `ServerEvent`), and mid-tool `SetPermissionMode` does not cancel/resolve a pending `PermissionRequest`.
- **H2, H3, H6, H7:** Not primary targets of E10.

### What Could Not Be Verified in E10
- **Live end-to-end execution with a scripted fake model / running Electron window:** Per Phase 1 rules ("Do not modify any source file") and the absence of a live scripted-provider harness inside `desktop/`, E10 was verified by full static call-graph and concurrency/mutex analysis across every layer of `desktop/` and `crates/`. Live interactive timing races (e.g., exact probability of `home-view.tsx:140`'s unawaited `setPermissionMode` or `ipc-client.ts:3431`'s unawaited `setModel` losing to `sendMessage` over the Unix socket) were not empirically measured.
