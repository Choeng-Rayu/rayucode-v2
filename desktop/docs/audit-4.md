# Audit 4: Session Switch Path & 10-Second Load Latency Analysis

**Scope:** Phase 1 read-only code audit per `desktop/docs/session-load-bug.md` (§3.2, §4 Step 5, & §6). Zero source files modified; zero trace instrumentation added.

---

## Executive Summary

When a user clicks a different session in RayuCode Desktop (cache miss on `runtimeTurns`), **first paint of the chat transcript waits on a serialized, single-lane pipeline in Electron main and the Rust daemon**, while the right Context panel runs on independent Electron IPC channels and paints immediately:

1. **Missing hover prefetch:** `SidebarProjectsPane` does not call `prefetchTraceTurns` on hover (`desktop/src/components/shell/sidebar-projects-pane.tsx:608-617`), even though `prefetchTraceTurns` is exported (`desktop/src/features/execution-trace/api/trace-api.ts:32-37`).
2. **Duplicate & non-chat work fired on every `activeSessionId` change:**
   - `SidebarProjectsPane` re-runs `listProjects()`, `listRecents()`, and `sidebar.getState()` (`desktop/src/components/shell/sidebar-projects-pane.tsx:130-154`), triggering **two** separate `bridge.harness.listSessions()` calls (`desktop/src/lib/ipc-client.ts:3325, 3363`), `workspace.getInfo()` (`L3328`), and sync `readSidebarState` (`desktop/electron/main.ts:450-452`).
   - `GettingStartedCard` re-runs `getGettingStarted()` (`desktop/src/components/shell/GettingStartedCard.tsx:109-111`).
   - `ChatStream` fires `ipcClient.fileChanges.get(effectiveSessionId)` (`desktop/src/features/execution-trace/components/chat-stream.tsx:425-446`), competing on the daemon's `attachQueue` even though `attach_session` already emits `FileChangesState` (`crates/rayucode-harness-api-server/src/translate.rs:2832-2835`).
3. **Electron main `attachQueue` contention + fresh socket per switch:** `daemonClient.getHistory` (`desktop/electron/daemon-client.ts:884-892`) shares `attachQueue` (`runSerialized`, `L678-682`) with `getFileChanges` (`L1048`) and prior rapid switches (no request ID or cancellation). Inside `ensureAttached` (`L766-794`), whenever switching from another session (`this.attachedSessionId !== null`), Electron main closes the old socket (`attachClient`, `L374-380`) and dials a **brand-new Unix socket** (`dialSocket`, `L784-786`, `L441-464`, `requestTimeoutMs: 15_000`).
4. **Cold resume + double full history replay (first payload discarded):**
   - `attachSession` translates into legacy `subscribe { target_session_id }` + `state` + `get_model_catalog` (`translate.rs:588-663`).
   - Rust `handle_resume_session` (`crates/rayucode-app-core/src/server/client_session.rs:1275-2057`) allocates a fresh `Agent` (`L1706`), loads `.json`+`.jsonl`, runs `restore_session_inner` (`crates/rayucode-app-core/src/agent/turn_execution.rs:1201-1305`), renders and sends **Full History #1** (`client_session.rs:1977-1994` -> `crates/rayucode-app-core/src/server/client_state.rs:987-1127`), and awaits `register_mcp_tools_for_dir` (`client_session.rs:2033-2040`).
   - Back in `translate.rs:2811-2837`, the bridge **discards `messages` and `images`** from that initial `history` reply (forwarding only `attachment_recovery`, `side_panel`, `applets`, and `file_changes`).
   - Electron `ensureAttached` then awaits `syncSessionTools` + `syncDesiredPermissionMode` (`desktop/electron/daemon-client.ts:789-792`), and `getHistory` issues `client.getHistoryWithImages(sessionId)` (`L890`), forcing the Rust daemon to render and serialize **Full History #2** (`client_state.rs:174-265`).
5. **Right Context panel & synchronous Electron main I/O:** `ContextPanel` (`desktop/src/features/inspector/api/inspector-api.ts:519-525`, query key `["inspector", "state"]` without `sessionId`) bypasses `attachQueue`, runs `workspace.getInfo()` (`desktop/electron/workspace-bridge.ts:76-85`), `git.getChanges()` (`desktop/electron/git-bridge.ts:342-387`, diffing up to 40 files with concurrency 6), and `extensions.list()` (`desktop/electron/storage-bridge.ts:345-482`, **synchronous** `readFileSync`/`readdirSync`/`statSync` across MCP configs, 4 skill roots, and 6 memory files on Electron's main thread), and hardcodes `"0%"` / `"0 / 200k tokens"` (`desktop/src/lib/ipc-client.ts:3842-3843`), while `SessionComposer` remains enabled (`desktop/src/features/sessions/components/composer.tsx:459-460, 1727`).

## 2. Evaluation of Hypotheses S1–S5 (`desktop/docs/session-load-bug.md` §3.2)

| # | Hypothesis | Supported by Code? | Cannot Be Decided Without a Runtime Trace |
|---|---|---|---|
| **S1** | Whole event log replayed on every switch | **Supported by code (on cache miss).** Cold switch calls `Session::load_for_resume` (`turn_execution.rs:1210`) + full `send_history_with_guard(..., HistoryPayloadMode::Full, ..., history_base: None)` **twice** (`client_session.rs:1977` and `daemon-client.ts:890` -> `client_state.rs:233`). Once cached in `runtimeTurns` (`ipc-client.ts:3555-3558`), switches skip the engine completely. | What fraction of wall-clock latency grows proportionally with message count / `.jsonl` bytes (`load_for_resume`, `render_messages`, `mapHistoryMessagesToTurns`). |
| **S2** | Engine attach/resume rebuilds state or spawns work per switch (fixed cost even for tiny sessions) | **Strongly supported by code (primary suspect for a 6-message session like `blossom` taking ~10s).** Every uncached switch dials a new Unix socket (`daemon-client.ts:785`), creates a fresh `Agent`, runs `restore_session_inner` (`AGENTS.md`, tool policy, hooks, compaction, `env_snapshot`), awaits `register_mcp_tools_for_dir` (`client_session.rs:2033-2040`), awaits `syncSessionTools` + `syncDesiredPermissionMode` (`daemon-client.ts:789-792`), and executes two full `get_history` round-trips. | Exact ms breakdown across `dialSocket`, `restore_session_inner`, `register_mcp_tools_for_dir`, `available_models_for_history`, `syncSessionTools`, `setPermissionMode`, and `handle_get_history`. |
| **S3** | History request queued behind other work | **Strongly supported by code.** Electron `attachQueue` (`daemon-client.ts:678-682`) globally serializes `getFileChanges` (`chat-stream.tsx:430`), `getHistory`, `attachSession`, `setPermissionMode`, and rapid switches (no cancellation / request IDs). Inside `ensureAttached` + `handle_resume_session`, history also waits behind MCP registration, tool sync, and permission sync. Additionally, `listLocalExtensions` (`storage-bridge.ts:345-482`) and `desktop-sessions.json` read/write (`L153-174, 204-224`) run **synchronously on Electron main's event loop**, whereas `git.getChanges` runs asynchronously via `execFile` bypassing `attachQueue` (explaining why the right panel renders while chat stays skeletonized). | Actual `attachQueue` wait ms, Electron main event-loop block time from `storage-bridge.ts`, and whether `getFileChanges` routinely enters `ensureAttached` before `getHistory`. |
| **S4** | Full render of all messages, diffs, tool outputs blocks main thread | **Structurally supported by code.** `ChatStream` (`chat-stream.tsx:781-791`) renders all turns via non-virtualized `allTurns.map(...)`, after synchronous `executionTurnListSchema.parse(raw)` (`trace-api.ts:26`). Unlikely to explain ~10s on tiny sessions like `blossom`, but scales with transcript size. | Renderer main-thread frame duration between `delivered_to_ui`, `first_paint`, and `full_paint` on small vs large sessions. |
| **S5** | Serialization or IPC of large payloads | **Structurally supported for large sessions.** Full `History` JSON (including inline `RenderedImage` base64 data) crosses daemon -> `harness-api-server` -> Electron main -> renderer **twice** on cold switch (first reply discarded at `translate.rs:2811-2837`). Unlikely to explain ~10s on small sessions. | Wire JSON encode/decode and Electron IPC transfer ms on large sessions. |

## 4. Gap Summary vs Target Pipeline (`desktop/docs/session-load-bug.md` §6)

- **Snapshot + windowing (§6.1 #1–3, #6):** Desktop uses full `get_history` without `history_base` / `recent_messages` (`recent_history_window` exists in `client_state.rs:476-563`, unused here) and transfers full history twice per uncached switch.
- **Request IDs / cancellation (§6.1 #3):** `attachQueue` (`daemon-client.ts:678-682`) runs switches FIFO with no `request_id` cancellation when the user clicks rapidly.
- **Hover prefetch & warm engine (§6.1 #5, #8):** `prefetchTraceTurns` (`trace-api.ts:32-37`) is uncalled in `sidebar-projects-pane.tsx:608-617`; `daemonClient.ensureAttached` opens a fresh Unix socket per switch.
- **Virtualized list (§6.1 #7):** `ChatStream` (`chat-stream.tsx:781-791`) renders all turns unconditionally.
- **Independent panels & loading honesty (§6.2–§6.3):** `ContextPanel` loads git/skills/memory independently of chat, but lacks `sessionId` scoping, hardcodes `"0%"` / `"0 / 200k tokens"` (`ipc-client.ts:3842-3843`), and `SessionComposer` accepts input during skeleton load (`composer.tsx:459-460, 1727`).

## 5. Proven vs Only Likely vs Could Not Check

### Proven
- Every file path and line number for the click-to-paint pipeline across Renderer (`App.tsx`, `sidebar-projects-pane.tsx`, `LeftSidebar.tsx`, `app-store.ts`, `GettingStartedCard.tsx`, `chat-stream.tsx`, `composer.tsx`, `trace-api.ts`, `harness-adapter.ts`, `ipc-client.ts`, `context-panel.tsx`, `inspector-api.ts`), Electron (`preload.cjs`, `main.ts`, `daemon-client.ts`, `git-bridge.ts`, `workspace-bridge.ts`, `storage-bridge.ts`), Harness API (`translate.rs`), and Rust Daemon (`client_lifecycle.rs`, `client_session.rs`, `session_manager.rs`, `turn_execution.rs`, `client_state.rs`).
- Double full-history execution on uncached switch (History #1 sent during `handle_resume_session`, `messages`/`images` dropped at `translate.rs:2811-2837`; History #2 requested by `daemon-client.ts:890`), fresh socket dial per switch, `attachQueue` contention with `fileChanges.get`, sync `storage-bridge.ts` FS I/O in Electron main, duplicate `listSessions()` in sidebar, and hardcoded `0%` context defaults.

### Only Likely
- That **S2** (per-switch resume/socket/MCP/tool-sync/double-history overhead) and **S3** (`attachQueue` serialization + Electron main sync FS blocking) account for most of the ~10-second delay on small sessions, while **S4** and **S5** matter primarily on large multi-hundred-turn transcripts.

### Could Not Check
- Actual per-span wall-clock timings on a tiny vs large session (no runtime instrumentation added or trace captured during Phase 1).
- Live daemon `[TIMING]` logs under `~/.rayu/logs/` (intentionally not read per read-only / workspace boundary).
